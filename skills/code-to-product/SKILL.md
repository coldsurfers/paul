# Code To Product

코드는 프로덕트를 만들기 위한 **브릿지**다. 코드 자체가 목적이 아니다.

## 핵심 방법 — 실물부터 그린다

다루는 대상이 현실에 형태가 있다면, 그 형태를 먼저 그리고 코드를 거기에 맞춘다.

티켓을 예로 들자. **티켓은 네모난 직사각형이고, 그 안에 정보가 들어있다.** 그러면 DB · TypeScript · React Component 모두에서 그 정보가 직관적이고 compact 하게 표현돼야 한다.

시안이나 실물 티켓을 볼 때 정보가 한눈에 들어오듯, React Component 에서도 한눈에 들어와야 한다. **그것이 곧 프로덕트와 직결된다.**

```
실물 (티켓 · 포스터 · 공연장)
  ↓ 형태를 그대로
DB 스키마
  ↓
TypeScript 타입
  ↓
React Component props
  ↓
화면
```

이 사슬에서 형태가 깨지는 지점이 있으면 그 지점이 버그와 유지보수 비용의 근원이다.

## 판정 질문

설계안을 놓고 스스로 묻는다.

1. **이 타입을 처음 본 사람이 실물을 떠올릴 수 있는가?** `Event { title, date, venue, lineup, poster, ticketLink }` 는 떠올릴 수 있다. `Event { meta, config, payload }` 는 못 떠올린다.
2. **props 가 한 화면에 들어오는가?** 스크롤해야 파악되는 props 는 컴포넌트가 두 개 이상을 그리고 있다는 뜻이다.
3. **이 추상화가 이미지를 그려주는가, 가리는가?** 가리면 지운다.
4. **단일 사용처인가?** 그렇다면 추상화하지 않는다.

## 안티패턴

| 하지 않는 것 | 이유 |
|---|---|
| 실물에 없는 중간 계층 (`*Manager`, `*Handler`, `*Service` 남발) | 이미지를 가린다 |
| 요청하지 않은 "유연성" · "설정 가능성" | 관리 포인트 증가 |
| 단일 사용처를 위한 추상화 | 인라인이 더 읽힌다 |
| 불가능한 시나리오를 위한 에러 처리 | 노이즈 |
| 200줄 넘는 컴포넌트 | 하나의 이미지가 아니다 |

200줄을 썼는데 50줄로 될 것 같으면 다시 쓴다.

## Image Making

라인 바이 라인이 아니라 **전체 이미지를 먼저 그린다.** 구현을 시작하기 전에 최종 형태(타입 시그니처 · 컴포넌트 트리 · 데이터 흐름)를 말로 설명할 수 있어야 한다. 설명이 안 되면 아직 이미지가 없는 것이고, 이미지가 없으면 코드를 쓰지 않는다.

## 실전 예 — 공연

```
Venue
 ├ Event (공연)
 │   ├ Lineup
 │   │   ├ Artist A
 │   │   └ Artist B
 │   ├ Poster
 │   └ Ticket Link
 └ 좌표 (geohash 기반)
```

포스터를 보면 제목 · 날짜 · 공연장 · 라인업이 한눈에 들어온다. 그래서 `Event` 타입도 그 네 가지가 상단에 온다. 좌표를 `Venue` 가 갖는 이유는 실물에서 주소가 공연장의 속성이지 공연의 속성이 아니기 때문이다.

컴포넌트도 같다 — `<EventCard event={event} />` 하나로 포스터 한 장의 정보량이 나와야 한다.
