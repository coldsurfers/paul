# Agentic Coding 워크플로

비자명한 작업은 반드시 이 순서를 따른다.

```
1. 이해    요청을 한 문장으로 재진술 — 어긋나면 코드 열기 전에 확인
2. Plan    방향이 갈리면 옵션 제시 → 사용자 결정
3. Spec    큰 작업은 specs/{앱또는패키지}/{기능}.md 먼저
4. 실행    스텝 단위로. 스텝마다 biome + type check 통과 후 다음
5. 반영    부가 요구사항은 즉시 반영하고 Spec 에도 반영
6. 보고    무엇을 / 왜 / 남은 결정. Spec 체크리스트 [x] 갱신
7. 커밋    명시적 요청이 있을 때만
```

2~3 은 `/paul:grill` · `/paul:spec`, 4~6 은 `/paul:step` 으로도 열린다 — 사용자 호출 전용이라 **제안만 하고 대신 부르지 않는다.**

## 세 가지 게이트 — 어기면 되돌아간다

- **Plan 없이 코딩하지 않는다** (2 없이 4 금지)
- **Spec 없이 큰 작업을 시작하지 않는다** (3 없이 4 금지)
- **검증 없이 다음 스텝으로 넘어가지 않는다** (4 안에서 스텝별)

## 네 가지 분기 — 새도 되는 지점

게이트가 "어기면 되돌아간다"면, 분기는 **새는 게 맞는 순간**이다. 억지로 직진하면 Plan 이 추측이 되거나 스펙이 안 끝난다.

| 언제 | 어디로 |
|---|---|
| 옵션의 트레이드오프를 **종이로 못 가릴 때** | 버리는 프로토타입 — 버릴 코드라고 **선언하고** 짠다. 결과는 Plan 의 입력이지 산출물이 아니다 |
| 갈림길이 셋 이상이거나 사용자가 "잘 모르겠다" 할 때 | `/paul:grill` 로 결정부터 뽑는다 — 옵션을 나열하지 말고 라운드로 심문한다 |
| 체크리스트가 **워크스페이스 넷 이상**으로 벌어질 때 | 스펙을 쪼갠다. 하나가 끝나야 다음이 시작되면 그건 스펙 둘이다 — 상대경로로 상호참조한다 |
| 컨텍스트가 차서 앞을 잊기 시작할 때 | **스텝 경계에서** 끊는다. 스텝 중간에 끊으면 검증 안 된 코드가 남는다 |

끊길 것을 전제로 Spec 은 두 가지를 남긴다 — 체크리스트의 `[x]`(어디까지 했나)와 「다음 세션이 열 파일」 앵커(어디를 여나). 둘 다 아래 Spec 절에 있다. 맥락이 사라진 다음 세션은 `[x]` 와 앵커만 읽고 이어붙는다.

## Plan

코드를 열기 전에 낸다. 방향이 갈리면 여기서 멈추고 사용자가 고른다.

```
## 이해
요청을 한 문장으로 재진술 — 어긋나면 여기서 멈춘다

## 현재 구조
관련 파일 · 데이터 흐름 (file:line 으로)

## 방향 옵션
A안 — 무엇을 / 트레이드오프
B안 — 무엇을 / 트레이드오프
추천: A안 (이유 한 줄)

## 스텝
1. [작업] → 검증: [체크]
2. [작업] → 검증: [체크]

## 남은 결정
사용자가 정해야 할 것
```

- **옵션이 하나뿐이면 옵션이라고 쓰지 않는다.** 억지로 대안을 만들지 않는다
- **현재 구조는 읽고 쓴다.** `file:line` 이 없는 Plan 은 추측이다
- 스텝의 검증란이 비면 그 스텝은 아직 안 쪼개진 것이다

Plan 만 내고 멈춰야 할 때 — 방향이 갈리거나, 사용자가 계획만 요청했을 때 — **코드를 쓰지 않는다.** 확정 신호를 받고 실행으로 넘어간다.

## Spec 파일

**위치:** 항상 레포 루트의 `specs/{앱또는패키지}/` 아래. 예) `specs/billets-admin/ddd-event-domain.md`
`docs/` 와 섞지 않는다 — 구분은 `paul-taste` 참조.

**언제:** 여러 워크스페이스에 영향 · 1일 이상 · 의사결정 분기가 있음 — 셋 중 하나라도 해당하면 작성한다.

**구조:**

```markdown
# {앱}: 제목

## 배경             — 왜 지금인가. 가설이 있으면 인용문으로 세운다
## 목표
### 비목표          — 이번에 안 하는 것
## 현재 흐름 (As-Is)
## 목표 흐름 (To-Be)
## 체크리스트
### {워크스페이스}   — 순서 = 의존 순서
- [ ] 할 일
- [x] 완료
## 변경 범위 요약    — 표
## 미결 사항         — 사용자가 정해야 할 것
```

**범위 표기:** ✅ 포함 · ⏸ 보류 · ❌ 제외.

네 가지가 스펙을 살린다.

**1. 비목표를 절로 둔다.** 표기보다 "이번엔 안 한다"를 문장으로 쓴 쪽이 스코프 크리프를 더 잘 막는다.

**2. 체크리스트는 워크스페이스별로 묶고, 그 순서가 곧 의존 순서다.**

```
### prisma-schema → ### data-models → ### server → ### api-sdk → ### client
```

이 순서가 그대로 스텝이 된다. 뒤집으면 중간에 타입이 없어 막힌다.

**3. 다음 세션이 열 파일을 앵커로 남긴다.** 인용 블록에 경로 + 무엇을 하는지.

```
> 관련 코드 위치:
> - packages/prisma-schema/prisma/schema.prisma (Comment 모델 추가)
> - apps/billets-server/src/routes/v2/comments.route.ts (신설)
```

**4. 결정의 근거는 그 자리에 인라인으로.** "slug 가 아닌 ID 를 박는 이유 — slug 가 운영 중 바뀌어도 스레드가 끊기지 않게." 나중에 왜 그랬는지 다시 묻지 않게 된다.

관련 스펙은 상대경로로 상호참조한다.

Spec 은 살아있는 문서다. 구조나 경로가 바뀌면 그때그때 갱신한다. 작업이 끝나고 몰아서 쓰지 않는다.

## 스텝 실행

각 스텝은 이렇게 선언하고 시작한다.

```
STEP 2 — Event 도메인 타입 정의
검증: pnpm turbo check:type 통과 + EventCard 렌더 확인
```

완료 후:

```bash
pnpm biome check --write <변경한 파일들>
pnpm turbo check:type
```

둘 다 통과해야 다음 스텝을 선언한다. 실패하면 실패했다고 출력과 함께 보고한다 — 넘어가지 않는다.

## 수술적 변경

**건드릴 것만 건드린다.** 모든 변경 라인이 사용자의 요청으로 직접 추적돼야 한다.

- 인접 코드 · 주석 · 포매팅을 "개선" 하지 않는다
- 깨지지 않은 것을 리팩토링하지 않는다
- 기존 스타일을 따른다. 내가 다르게 짤 것 같아도 따른다
- 무관한 데드 코드를 발견하면 **말만 하고 지우지 않는다**
- 내 변경 때문에 생긴 고아(미사용 import · 변수 · 함수)만 정리한다

## 보고 형식

```
## 한 것
- 무엇을 (파일:라인)

## 왜
- 선택의 이유 한 줄

## 남은 결정
- 사용자가 정해야 할 것
```

## 커밋

명시적 요청이 있을 때만. 형식과 pre-push 체크리스트는 `paul-taste` 스킬 참조.
