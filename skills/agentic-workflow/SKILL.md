# Agentic Coding 워크플로

비자명한 작업은 반드시 이 순서를 따른다.

```
1. 이해    요청을 한 문장으로 재진술 — 어긋나면 코드 열기 전에 확인
2. Plan    방향이 갈리면 옵션 제시 → 사용자 결정
3. Spec    큰 작업은 specs/{앱또는패키지}/{기능}.md 먼저
4. 실행    스텝 단위로. 스텝마다 biome + type check 통과 후 다음
5. 반영    부가 요구사항은 즉시 반영하고 Spec 에도 반영
6. 보고    무엇을 / 왜 / 남은 결정. Spec 체크리스트 [x] 갱신
7. 커밋    명시적 요청이 있을 때만
```

## 세 가지 게이트 — 어기면 되돌아간다

- **Plan 없이 코딩하지 않는다** (2 없이 4 금지)
- **Spec 없이 큰 작업을 시작하지 않는다** (3 없이 4 금지)
- **검증 없이 다음 스텝으로 넘어가지 않는다** (4 안에서 스텝별)

## Spec 파일

**위치:** 항상 레포 루트의 `specs/{앱또는패키지}/` 아래. 예) `specs/billets-admin/ddd-event-domain.md`

**언제:** 여러 워크스페이스에 영향 · 1일 이상 · 의사결정 분기가 있음 — 셋 중 하나라도 해당하면 작성한다.

**구조:**

```markdown
# 제목

## 목표
## 현재 문제 (선택)
## 목표 구조
## 레이어/설계 설명
## 체크리스트
### 단계별 항목
- [ ] 할 일
- [x] 완료
## 변경 범위 요약 (표)
```

**범위 표기:** ✅ 포함 · ⏸ 보류 · ❌ 제외 를 명시해 스코프 크리프를 막는다.

Spec 은 살아있는 문서다. 구조나 경로가 바뀌면 그때그때 갱신한다. 작업이 끝나고 몰아서 쓰지 않는다.

## 스텝 실행

각 스텝은 이렇게 선언하고 시작한다.

```
STEP 2 — Event 도메인 타입 정의
검증: pnpm turbo check:type 통과 + EventCard 렌더 확인
```

완료 후:

```bash
pnpm biome check --write <변경한 파일들>
pnpm turbo check:type
```

둘 다 통과해야 다음 스텝을 선언한다. 실패하면 실패했다고 출력과 함께 보고한다 — 넘어가지 않는다.

## 수술적 변경

**건드릴 것만 건드린다.** 모든 변경 라인이 사용자의 요청으로 직접 추적돼야 한다.

- 인접 코드 · 주석 · 포매팅을 "개선" 하지 않는다
- 깨지지 않은 것을 리팩토링하지 않는다
- 기존 스타일을 따른다. 내가 다르게 짤 것 같아도 따른다
- 무관한 데드 코드를 발견하면 **말만 하고 지우지 않는다**
- 내 변경 때문에 생긴 고아(미사용 import · 변수 · 함수)만 정리한다

## 보고 형식

```
## 한 것
- 무엇을 (파일:라인)

## 왜
- 선택의 이유 한 줄

## 남은 결정
- 사용자가 정해야 할 것
```

## 커밋

명시적 요청이 있을 때만. 형식과 pre-push 체크리스트는 `paul-taste` 스킬 참조.
