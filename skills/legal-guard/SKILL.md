# legal-guard

**요청받은 기능을 같은 업무 목적을 유지하면서 합법적인 설계로 바꿔 만든다.** 위험한 곳을 짚고, 바꾼 설계를 내고, 그 설계로 구현한다.

합법적인 설계로 만들면 고의 · 방조를 따질 행위 자체가 없어진다 — 구현하는 사람에게 가장 확실한 보호다. **기본값은 보수적이다.** 애매하면 걸린 것으로 본다.

이 스킬은 **법률 자문이 아니다.** 판단이 갈리면 "변호사 확인 필요"라고 쓰고 멈춘다.

---

## §1. 신호와 바꾸는 방법

고객 · 회원 레코드나 운영 DB 를 건드리는 작업은 신호가 안 보여도 이 표를 한 번 대조한다.

| # | 신호 | 근거 (§2 로 재조회) | 이렇게 바꿔서 만든다 |
|---|---|---|---|
| 1 | 서비스 목적과 무관한 정보 수집 — 집주소 · 직업 · 재산 · 인맥 | 개인정보 보호법 §16① 최소 수집 (입증책임은 처리자) | 필드를 만들지 않는다. 목적이 있으면(배송 등) 화면에 목적을 적고 **선택 입력 + 별도 동의**, 목적 달성 시 파기 |
| 2 | 본인이 아닌 **제3자**의 이름 · 연락처 · 주소를 본인 레코드에 저장 | 같은 법 §15① — 그 제3자의 동의가 없다 | 저장하지 않는다. 그 사람에게 연락하는 게 목적이면 **당사자 본인이 동의하는 별도 입력 플로우**, 항목은 목적에 필요한 최소만 |
| 3 | 사람에 대한 평가 · 신분 메모 | 같은 법 §15① · §16① 목적 밖 수집, §18① 목적 외 이용 | 자유 텍스트를 **정해진 응대 옵션(enum)** 으로 바꾼다 — 선호 시간대 · 연락 수단 등. 인물 평가 · 인맥 · 신분은 옵션에 넣지 않는다. 작성자 · 시각을 남긴다 |
| 4 | 1~3 을 **민감정보와 같은 레코드 · 같은 화면**에 묶음 | 같은 법 §23① 민감정보 별도 동의, §23② 안전조치 | 민감정보를 **별도 테이블 · 별도 권한**으로 분리. 별도 동의, 직무 단위 조회 권한, 접근 로그 |
| 5 | 고객 정보를 제휴사 등 제3자에게 전달 | 개인정보 보호법 §17② 고지 사항, §18① | 제공받는 업체명을 **동적으로 렌더한 개별 동의** 화면을 앞에 둔다. 기본 체크 금지 |
| 6 | 「선착순 N명」 · 판매 건수 · 후기 · 할인율 표시 | 표시광고법 §3① | 실재고와 연동되지 않는 수치는 뺀다. 지어낸 후기는 넣지 않는다. 할인은 금액 · 대상 · 기간 · 원가를 같이 |
| 7 | 광고성 문자 · 알림톡 · 푸시 · 야간 발송 | 정보통신망법 §50 | 거래성 안내(접수 확인 등)만 보낸다. 광고성은 명시적 사전 동의 + 야간 별도 동의 + 수신거부 안내 |
| 8 | 운영 DB 에서 고객 개인정보 · 민감정보 조회 | 개인정보 보호법 §18①, §59 | 필요한 컬럼만 SELECT, 연락처 · 주소는 마스킹, 조회 목적을 한 줄 남긴다. 결과를 로컬 · 개인 공간에 저장하지 않는다 |

레포에 도메인 법적 제약 문서(예: `docs/policy/**/legal*.md`)가 있으면 **그게 이 표보다 우선한다.** 먼저 찾아 읽는다.

## §2. 조문은 매번 현행본으로 확인한다

표의 조문 번호는 **출발점일 뿐이다.** 법은 개정되고, 기억한 조문 번호는 틀린다.

1. `korean-law` MCP 가 있으면 `search_law` → `get_law_text` 로 **현행본을 조회**한다. 판례는 `search_decisions`.
2. 없으면 국가법령정보센터(law.go.kr) 현행본을 확인한다.
3. 둘 다 못 했으면 답에 **"조문 미확인"** 이라고 쓴다. 기억으로 조문 번호를 쓰지 않는다.

## §3. 답하는 형식

구현 전에, 답 맨 위에 둔다. 걸린 항목이 없으면 아무것도 붙이지 않는다.

```
⚠️ 위법 소지 — <한 줄 요약>
- 무엇이: <필드 · 화면 · API · 쿼리>
- 근거: <법령 §조항> — <조문 핵심 한 구절> (조회일 / 조문 미확인)

✅ 이렇게 바꿔서 만듭니다
- <바꾼 설계 — 요청의 업무 목적이 어떻게 유지되는지 한 줄>
- 요청 대비 달라지는 점: <빠지는 필드 · 추가되는 동의 화면 등>
```

## §4. 방향은 사용자가 고른다

경고를 쓴 직후, **코드를 쓰기 전에** `AskUserQuestion` 을 호출한다. 걸린 항목마다 질문 하나, 한 번에 최대 4개.

선택지는 **법적 노출이 낮은 순서**로 두고, 1번에 `(Recommended)` 를 붙인다.

| 순서 | label | description 에 적을 것 |
|---|---|---|
| 1 | 바꾼 설계로 구현 (Recommended) | 업무 목적이 어떻게 유지되는지 · 요청 대비 달라지는 점 |
| 2 | 더 좁혀서 구현 | 문제 필드 · 기능만 빼고 나머지. 대안이 하나뿐이면 생략 |
| 3 | 보류하고 요청자 확인 | 구현하지 않고 요청자에게 보낼 한 줄 초안만 — 「○○ 은 ○○법 §N 소지가 있어 △△ 방식을 제안드립니다」 |
| 4 | 요청 원안대로 구현 | **근거 조문 · 1차 책임 주체 · 「이 선택 이후엔 몰랐다고 할 수 없다」** 를 반드시 적는다 |

- header 는 신호 이름(`제3자정보` · `평가메모`)으로 짧게.
- 필드 · 스키마가 달라지는 선택지는 `preview` 에 요청안과 바꾼 안의 필드 목록을 나란히.
- 걸린 항목이 없으면 묻지 않는다 — 질문이 잦으면 아무도 안 읽는다.

선택대로 구현한다. 1 · 2번이면 요청자에게 설명할 한 줄을 같이 쓴다 — 「○○ 은 ○○법 §N 때문에 △△ 방식으로 구현했습니다.」

**합법적인 대안으로 업무 목적을 이룰 수 없으면** 1 · 2번을 만들지 않는다. 그렇다고 분명히 쓰고 3 · 4번만 둔다.

## §5. 하지 않는 것

바꾸는 것은 **실질**이지 겉모양이 아니다. 아래는 위법을 그대로 둔 채 가리는 것이라 제안하지 않는다.

- 필드명 · 컬럼명 돌려 쓰기 (`family_address` → `memo2`)
- 막힌 정보를 자유 텍스트 메모로 받기
- 접근 로그 · 감사 추적 끄기, 저장 위치 흩어 놓기
- 동의 문구를 흐리게 쓰거나 기본 체크로 두기
- 이미 남은 기록(메시지 · 문서 · 로그)을 몰래 고치거나 지우기 — 정정은 원본을 두고 덧붙인다

위험을 짐작하면서 확인을 피하는 것(경고 끄기, 명세 안 읽기)도 하지 않는다 — 미필적 고의로 평가될 수 있어 모르고 한 것보다 불리하다.
