# Code Review

**판정만 한다. 고치지 않는다.** 리뷰와 수정이 한 턴에 섞이면 사용자가 무엇에 동의했는지 사라진다.

이 스킬은 **판정 기준을 새로 만들지 않는다.** 기준은 각 축의 스킬에 이미 있고, 여기 있는 건 **정본을 어디서 찾고 · 어떤 순서로 어느 렌즈를 대고 · 나온 것을 어떻게 가르고 몇 개나 쓰는가**다.

## 0. 경계

| 하는 것 | 하지 않는 것 |
|---|---|
| 읽고 · 대조하고 · 판정한다 | 파일을 고친다 |
| 고칠 방향을 한 줄로 제시한다 | 패치를 대신 적용한다 |
| 못 본 곳을 못 봤다고 쓴다 | 안 읽은 파일을 읽은 척 판정한다 |

수정은 **사용자가 지시한 뒤** 별도 턴에서 한다. "고쳐드릴까요?" 로 끝내고 멈춘다. 반영 절차의 정본은 `paul-review-fix` 다.

## 0.5. 정본은 어디에 있는가 ★

리뷰는 *"내 취향과 다르다"* 가 아니라 **"정본과 다르다"** 를 말하는 일이다.
그래서 렌즈를 대기 전에 **정본이 어디 있는지부터 정한다.** 이걸 건너뛴 리뷰는 전부 취향 싸움이 된다.

| | 내 레포 | 남의 레포 — 오픈소스 · 인수인계 · 합류 첫 주 |
|---|---|---|
| 정본 | `paul-*` 스킬 · Biome · 디자인 토큰 · changeset | **그 레포 자신** |
| 근거 대는 꼴 | "`paul-frontend` 4절" | "옆 화면은 이렇게 합니다" + 파일 위치 |
| 근거를 못 대면 | 쓰지 않는다 | 쓰지 않는다 |

**남의 레포에 `paul-*` 을 근거로 들지 않는다.** 그 레포는 내 규약에 동의한 적이 없다.
"내가 다르게 쓸 것 같다" 는 근거가 아니다.

남의 레포의 정본은 이 순서로 찾는다. **읽기 전에 찾는다.**

1. **준 것** — 봉인된 패키지 · `lib/` · `vendor/` · 디자인시스템 · 이미 있는 훅.
   있는 걸 안 쓰고 새로 만들었으면 **그 자체가 지적**이다
2. **설정** — `eslintrc` · `tsconfig` · `prettierrc` · `package.json`. 레포가 이미 깔아둔 레일
3. **옆 파일** — 같은 종류의 파일 셋을 나란히 놓는다. A·B 는 하는데 **C 만 빠진 것**이 여기서 보인다
4. **계약** — 서버 핸들러 · API 타입 · 목 데이터 · 요청 예시. **도메인 규칙이 여기 적혀 있다**
5. **테스트** — 무엇을 보장하기로 했는가. 테스트가 보는 곳이 그 레포가 지키기로 한 선이다

> 내가 쓰지 않은 코드를 통째로 읽어야 하면 [`references/foreign-codebase.md`](references/foreign-codebase.md) 를 연다 —
> 정본을 찾는 실행 절차와 도메인 함정 목록이 거기 있다.

## 1. 읽는 순서

렌즈를 대기 전에 **범위를 먼저 세운다.** 순서가 곧 신뢰도다.

1. **무엇이 바뀌었나** — 변경 파일 목록. 커밋 전이면 워킹 트리, PR 이면 diff. 남의 레포 전체면 §0.5 의 1~5
2. **어디에 놓였나** — 새 파일이 어느 슬라이스·디렉터리에 들어갔는가 (`paul-frontend` Ⅱ부)
3. **경계면 대조** — 타입 선언 한쪽만 읽고 판정하지 않는다. API 응답 ↔ DTO ↔ 훅 반환 ↔ props 를 **같이 열어** 모양이 맞는지 본다
4. **본문** — 컴포넌트 · 훅 안쪽 (`paul-frontend` Ⅲ부)
5. **주변** — 이 변경으로 고아가 된 것(끊긴 import · 안 쓰이게 된 export)이 남았는가

3번을 건너뛰면 리뷰가 린터로 내려앉는다. **한 파일 안에서 보이는 문제는 도구가 이미 잡는다** — 사람이 붙는 이유는 파일을 건너뛰는 불일치다.

## 2. 렌즈

각 항목의 **정본은 오른쪽 스킬**이다. 판정이 애매하면 그 스킬을 열어 확인하고, 여기 요약과 다르면 정본이 이긴다.
**남의 레포면 오른쪽 칸이 통째로 §0.5 의 "그 레포 자신" 으로 바뀐다** — 보는 축만 빌리고 근거는 거기서 댄다.

| 렌즈 | 무엇을 보는가 | 정본 |
|---|---|---|
| 세우는 순서 | 화면 파일에서 새 개념이 태어나지 않았는가 · 여백이 `margin` 이 아니라 프리미티브인가 · 경로가 타입으로 잠겼는가 | `paul-frontend` Ⅰ |
| 배치 | 유닛 하나 = 디렉터리 하나인가 · 배럴이 `export *` 뿐인가 · import 가 슬라이스 경계를 뚫지 않는가 | `paul-frontend` Ⅱ |
| 컴포넌트 | 핸들러·파생값이 메모됐는가 · 레이아웃이 도메인 타입을 받지 않는가 · 껍데기가 로딩·에러를 쥐는가 · 색이 토큰인가 · key 가 도메인 id 인가 | `paul-frontend` Ⅲ |
| 모델링 | props 가 한 화면에 들어오는가 · 이름이 실물과 맞는가 · 타입에 실물의 형태가 비치는가 | `code-to-product` |
| 스택 | Biome 정본을 우회하지 않았는가 · `npm`/`yarn` 이 섞이지 않았는가 · changeset 이 필요한 변경인가 | `paul-stack` |
| 네이밍·커밋 | 파일·심볼 이름 · 커밋 메시지 형식 | `paul-taste` |
| 범위 | 요청과 무관한 줄이 바뀌지 않았는가 (`NORMS.md` 3장) | — |

렌즈에 없는 셋은 **여기가 정본**이다.

**계약** — 타입이 통과하고 린터가 조용한 자리다. **사람이 리뷰에 붙는 이유가 여기다.**
- **양쪽 계산** — 클라가 계산한 값을 서버가 **다시 계산해 거절**하는가. 그러면 두 식이 같아야 한다. 한쪽만 고치면 배포 후에 터진다
- **인덱스 결합** — `labels[i]` ↔ `prices[i]` 처럼 배열 둘이 **순서로만** 묶여 있는가. 한쪽이 늘면 조용히 어긋난다
- **단위** — `amountInCents` · `rateInBp`. **단위가 이름에 없는 숫자**가 경계를 넘는가. 스케일이 어긋나면 표시단에서 통째로 틀린다
- **레이아웃 값으로 데이터 순회** — `Array.from({ length: col })`. 지금 데이터라서 **우연히** 맞는가
- **상태 분기 누락** — 목 데이터·시나리오에 있는 상태(진행중 · 빈 상태 · 404)를 화면이 다루는가

**타입 안정성**
- `any` — 불가피하면 **이유 주석**이 붙어 있는가. 없으면 필수 수정
- `as` 단언 — 좁히는 근거가 코드에 있는가. 런타임 검증 없는 단언은 거짓말이다
- 손으로 쓴 타입이 스키마·코드젠 산출물과 **병존**하는가 (`paul-frontend` 5절)

**보안**
- 입력이 쿼리·마크업·경로에 그대로 흘러들어가는가
- 토큰 · 키 · 개인정보가 로그 · 응답 · 클라이언트 번들에 새는가
- 인증·인가 검사가 **새 엔드포인트에** 빠졌는가

## 3. 필수와 권고를 가르는 것

**"틀렸다"와 "나라면 다르게 쓴다"는 다르다.** 후자를 필수에 올리면 리뷰가 취향 강요가 된다.

| | 조건 |
|---|---|
| **필수 수정** | 지금 깨져 있거나 · 배포하면 깨지거나 · 데이터·권한이 새거나 · 규약의 **정본을 정면으로 위반**(Biome 우회 · 하드코딩 hex · 병존하는 타입)한 것 |
| **권고** | 지금은 돌아가지만 자라면 아플 것 — 200줄 넘은 파일 · 아직 안 뚫린 경계 · 이름이 실물과 살짝 어긋난 것 |
| **안 씀** | 근거를 정본에서 못 대는 것. 개인 취향 · 스타일 선호 · "요즘은 이렇게 한다" |

**확신이 없으면 권고로 내린다.** 확신 없는 필수는 사용자의 시간을 뺏고 리뷰 전체의 신뢰를 깎는다.

### 몇 개까지 쓰는가 ★

**필수는 세어서 낸다.** 나쁜 코드에선 지적이 50개 나온다 — 50개를 다 쓰면 읽는 사람이 **무엇부터 고칠지 모른다.**

| 필수 개수 | 의미 | 쓰는 법 |
|---|---|---|
| 0~5 | 정상 | 그대로 낸다 |
| 6 이상 | 리뷰가 아니라 재작성 요청이다 | **가장 아픈 5개만 내고**, 나머지는 "같은 원인" 한 줄로 묶는다 |

줄이는 기준은 하나다 — **"안 고치면 무엇이 터지는가."** 터지는 게 없으면 권고다.
권고도 같다: **묶을 수 있으면 묶는다.** "여기저기 하드코딩 색" 은 한 항목이지 열 항목이 아니다.

## 4. 출력

```
## 필수 수정
- [파일:라인] 문제 → 해결 방향

## 권고
- [파일:라인] 개선 포인트

## 통과
- 잘 된 부분 한 줄
```

- **문제에 집중한다.** 칭찬으로 분량을 만들지 않는다
- **지적할 게 없으면 없다고 쓴다.** 채우기 위한 지적을 만들지 않는다 — 빈 리뷰는 실패가 아니다
- 못 본 범위가 있으면 마지막에 한 줄로 밝힌다 — "`packages/*` 는 안 봤다"
- 같은 문제가 여러 파일에 있으면 **한 항목으로 묶고** 파일을 나열한다

### 어떻게 쓰는가

**동료에게 쓰는 글이다.** 판정 근거가 문장 안에 있어야 한다.

| ✗ | ✓ |
|---|---|
| "잘못된 구현입니다" | "총액을 화면에서만 계산하는데, 서버가 같은 값을 재계산해 다르면 400 을 냅니다" |
| "타입이 안전하지 않습니다" | "`as` 로 좁히는데 런타임 검증이 없어서, 응답이 바뀌면 여기서 안 터지고 렌더에서 터져요" |
| 항목마다 정답 코드 | **방향 한 줄** — 어떻게 고칠지는 짠 사람이 정한다 |

**모르면 모른다고 쓴다.** *"이 부분은 의도를 몰라 판정을 못 했습니다 — 왜 이렇게 두셨는지 궁금해요"* 는 감점이 아니다.
안 읽고 단정한 것이 감점이다.

## 판정

1. 이 지적의 근거를 **정본에서 댈 수 있는가** — 못 대면 쓰지 않는다
2. 남의 레포인가 — 그렇다면 근거가 **그 레포 안**에 있는가 (§0.5)
3. 이건 **깨진 것인가, 자라면 아픈 것인가** — 필수와 권고가 갈린다
4. 필수가 **몇 개인가** — 6개를 넘으면 줄이고 묶는다
5. 경계면을 **양쪽 다 열어 봤는가** — 한쪽만 보고 불일치를 말하지 않는다
6. 이 파일을 **실제로 읽었는가**
7. 지금 내가 **고치려 하고 있지 않은가**

## 안 하는 것

| 하지 않는 것 | 이유 |
|---|---|
| 리뷰하며 바로 수정 | 사용자가 무엇에 동의했는지 사라진다 |
| 남의 레포에 `paul-*` 을 근거로 들기 | 그 레포는 내 규약에 동의한 적이 없다 |
| 필수를 세지 않고 다 쏟기 | 무엇부터 고칠지가 사라진다 |
| 채우기 위한 지적 | 진짜 문제가 묻힌다 |
| 취향을 필수로 올리기 | 리뷰가 강요가 된다 |
| 한쪽 파일만 보고 타입 불일치 단정 | 대조하지 않은 판정은 추측이다 |
| 요청 범위 밖 파일까지 훑기 | 리뷰도 수술적이다 (`NORMS.md` 3장) |
| 기준을 여기서 새로 만들기 | 정본이 갈라진다 |
