`$ARGUMENTS` 에 대한 Plan 과 Spec 초안을 만든다. **코드는 쓰지 않는다.**

## 순서

1. **이해** — 요청을 한 문장으로 재진술한다. 어긋나면 여기서 멈추고 확인한다.
2. **현재 구조 파악** — 관련 파일·데이터 흐름을 `file:line` 으로 짚는다. 광범위한 탐색이 필요하면 서브 에이전트를 띄우기 전에 **먼저 허락을 구한다**.
3. **방향 옵션** — 갈림길이 있으면 A/B 안과 트레이드오프를 제시하고 추천을 붙인다. 대안이 실제로 하나뿐이면 억지로 만들지 않는다.
4. **Spec 필요 판정** — 여러 워크스페이스 영향 / 1일 이상 / 의사결정 분기 중 하나라도 해당하면 Spec 을 만든다. 아니면 Plan 만 내고 끝낸다.
5. **경로 확인** — `specs/{앱또는패키지}/{기능}.md` 경로를 제시하고 사용자 승인 후 쓴다.

## Spec 구조

```markdown
# 제목

## 목표
## 현재 문제 (선택)
## 목표 구조
## 레이어/설계 설명
## 체크리스트
### 단계별 항목
- [ ] 할 일
## 변경 범위 요약 (표)
```

범위는 ✅ 포함 · ⏸ 보류 · ❌ 제외 로 명시해 스코프 크리프를 막는다.

## 끝난 뒤

Spec 을 쓴 다음 **구현으로 넘어가지 않는다.** 첫 스텝을 제안하고 멈춘다.
